# 非同期ファイル処理基盤の設計

## 目的

Terraformで複数のAWSリソースが連携する構成を設計し、AIが生成するインフラコードに対して、実装前の設計レビューがどの程度有効かを検証する。

実際のAWSは使用せず、AWS互換のローカルエミュレーターであるFlociへデプロイする。クラウドアカウント、認証トークン、利用料金を必要とせず、Terraformによる作成から動作確認までローカルで完結させる。

## スコープ

JSONファイルを投入すると非同期に処理し、結果と処理状態を保存する基盤を対象とする。

処理の流れは次のとおりとする。

1. 入力用S3バケットへJSONファイルを投入する。
2. S3イベントをSQSキューへ送る。
3. LambdaがSQSメッセージを受け取り、JSONを検証する。
4. 正常なファイルは、処理結果を結果用S3バケットへ保存する。
5. 処理状態をDynamoDBへ保存する。
6. 規定回数失敗したメッセージをDead Letter Queueへ送る。

Terraformでは、次のリソースとその連携を管理する。

- 入力用および結果用S3バケット
- SQSキューおよびDead Letter Queue
- Lambda関数
- DynamoDBテーブル
- LambdaのIAMロールおよび必要最小限のポリシー
- S3イベント通知
- SQSのイベントソースマッピング

## 対象外

- 実際のAWSへのデプロイ
- FlociとAWSの完全な互換性の保証
- Web UIおよびHTTP API
- ユーザー認証
- 複数環境への展開
- リモートのTerraform state
- 監視ダッシュボードおよび外部通知
- 大容量ファイル、並列性能、負荷試験
- 汎用Terraformモジュールとしての提供

## 採用する方針

### SQSを介した非同期処理

S3からLambdaを直接呼び出さず、Standard SQSキューを介する。メッセージの再試行と失敗時の隔離を構成として確認でき、複数リソースの責務と連携をレビューする題材になるためである。S3がキューへ送信できるよう、入力バケットに送信元を限定したSQSキューポリシーもTerraformで管理する。

### 処理状態をDynamoDBへ保存

入力ファイルを識別するキー、処理状態、更新日時、結果の保存先を記録する。結果ファイルそのものはS3へ保存し、DynamoDBには保存しない。

### 最小限のLambda処理

LambdaはPythonで実装する。JSONとして読み込めることを検証し、受け取った内容に処理日時を加えて結果用バケットへ保存する。業務ロジックの複雑さを実験へ持ち込まない。タイムアウトは10秒、SQSイベントソースのバッチサイズは1とする。

### ローカル固有設定の分離

TerraformのAWSリソース定義は、可能な範囲で通常のAWS Providerの記述を保つ。Flociのエンドポイントやダミー資格情報など、ローカル実行に必要な設定は明確に分離する。

### IAMを必要最小限にする

Lambdaには、対象キューの受信と削除、対象バケットの読み書き、対象テーブルの更新、ログ出力に必要な権限だけを与える。ワイルドカードによる全リソース許可は使用しない。S3からSQSへの送信権限はLambdaのIAMロールではなく、キューのリソースポリシーで管理する。

## 受け入れ条件

- Docker環境でFlociを起動できる。
- Terraformの初期化、plan、applyがローカルで成功する。
- 入力用S3バケットへ正常なJSONを投入すると、結果用S3バケットへ結果が保存される。
- 正常処理後、DynamoDBで処理状態と結果の保存先を確認できる。
- 不正なJSONを投入すると再試行され、最終的にDead Letter Queueへ送られる。
- LambdaのIAMポリシーが対象リソースに限定されている。
- Terraformのfmt、validateおよびlintを自動実行できる。
- ローカル環境を作り直して、同じ確認手順を再現できる。

## 検証方法

- docker composeでFlociを起動し、ヘルスチェックを確認する。
- Terraformのfmt、validate、lint、plan、applyを実行する。
- AWS CLIの接続先をFlociへ向け、正常なJSONと不正なJSONをそれぞれ入力用バケットへ投入する。
- S3、DynamoDB、SQSをAWS CLIで確認し、受け入れ条件どおりに処理されたことを確認する。
- Terraformの差分全体をセルフレビューし、不要なリソース、過剰な抽象化、広すぎる権限がないことを確認する。
- Flociで成功した結果は、実際のAWSでの動作保証とは分けて記録する。

## 設計レビューで確定した事項

- DynamoDBは、複数リソースが連携する設計を検証するため残す。入力のS3オブジェクトキーを主キーとし、処理状態、更新日時、結果の保存先を記録する。
- S3イベントとSQSイベントソースマッピングは、Flociで実際に疎通を確認する。未対応だった場合は別経路で回避せず、互換性上の実験結果として記録して作業を止める。
- Lambdaのタイムアウトは10秒、SQSのvisibility timeoutは60秒とする。
- Dead Letter Queueへ移動するmaxReceiveCountは5とする。
- バッチサイズは1とし、部分バッチ応答は導入しない。
- S3イベントが重複する可能性は許容する。結果のS3キーとDynamoDBの主キーを入力オブジェクトキーから決定し、同じ入力の再処理で同じ保存先を上書きする。
- LambdaはPythonで実装し、Terraformのarchive_fileでパッケージを作成する。
- AWS Providerのエンドポイントとダミー資格情報だけをFloci向けprovider設定へ分離し、リソース定義を環境別モジュールには分割しない。
